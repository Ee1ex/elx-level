# 个人开发执行循环

本文件定义 LEVEL 1–3 在已确认范围内的连续执行方式。它不改变 `LEVEL.md` 的责任模式，也不放宽硬性安全边界。

## 三种对外策略

- `AUTO`：事实、范围和目标已确认，动作可恢复且未触发硬边界；连续完成实现、运行、观察、调整、记录和本地验证。
- `CONFIRM`：方向存在多个实质方案，或范围、架构、数据、权限、安全、兼容、生产、外部写入和 Release 条件变化；先展示事实与选项。
- `MANUAL_ONLY`：Agent 只准备，不执行生产数据、密钥、支付、不可逆迁移、生产部署、公开发布、对外发送、Merge、Release 等动作。

内部 R1–R4 可以保留在状态中用于兼容和判断，但 LEVEL 1–3 的普通进度不逐轮展示风险编号。

## 连续循环

1. 读取规则、文档地图、当前状态、相关实现、测试和 Git 状态。
2. 确认本切片目标、范围、不做、验收和受影响的稳定认知入口。
3. 建立修改前基线；功能或修复先写失败测试并确认失败原因。
4. 做最小完整修改，运行相关检查，观察真实行为并调整。
5. 检查 Diff，只保留当前任务内容；同步稳定认知层和演进记录层。
6. LEVEL 1/2 在验证全部通过后，立即创建只包含当前任务文件的本地提交（当前分支含默认分支均可，见 `git-and-draft-pr.md` 的切片提交纪律）；未验证不提交。满足 DoD 后继续下一切片；功能完成、测试通过和本地提交不形成自动人工 Gate。
7. 版本集中验收后准备 GitHub 交付计划，远程动作前统一确认。

## 各 LEVEL 节奏

- LEVEL 1：快速实现—运行—观察—调整；每个小功能留下 Progress/Change Record，集中做核心路径和打包验收。
- LEVEL 2：按 Phase 0 → Phase N 和范围冻结推进；Phase DoD 满足后自动进入下一 Phase。
- LEVEL 3：沿用仓库 Issue、PR、CHANGELOG、ADR 和测试事实；以最小兼容修改、受影响回归和交接为闭环。

## 回环规则

验证、验收或复盘发现需求、方案或计划不成立时，回到受影响阶段重新确认，不带着已证伪的方向继续实现：需求或范围变化先更新需求文档（LEVEL 1 更新 Project Brief，LEVEL 2 回写 PRD）并重新确认；方案或计划不成立重新拆解任务再实现。小修小补使用 Change Record 记录即可，不推倒重来。

## 重新确认条件

一次有界授权持续有效。只有事实变化、范围扩大、核心方向或架构变化、数据语义或权限安全变化、公共兼容性破坏、外部目标变化或硬性边界触发时，策略才从 `AUTO` 切换为 `CONFIRM` 或 `MANUAL_ONLY`。
