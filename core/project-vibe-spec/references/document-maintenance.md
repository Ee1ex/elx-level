# 文档维护规则

## 先确定实际路径

`DOCUMENT_MAP.md` 是模板职责与项目实际路径之间的唯一索引。项目可以采用 `PDD.md`、`Notus_PDD.md`、`specs/product.md` 或既有目录；实施和交付一律引用映射后的真实路径。

首次接入时优先沿用已有的近似目录。只有缺少该职责时才创建模板目录，不能把同类事实拆到两套台账中。

记录粒度唯一依据是主包 `references/documentation-contract.md`。下表说明事实放在哪里，不是每轮必读或必写清单；小任务的一条日志或一份 Change/Bug 已足够时，不追加需求台账。

文档地图只负责导航：标出当前功能域需要阅读的事实文档、主要实现和验证入口。它不记录产品或技术结论，不替代需求、PDD、PRD、UI 或流程文档，也不能改变项目已有的文档优先级。

## 文档职责

| 文档 | 记录内容 | 不记录内容 |
|---|---|---|
| Requirements Ledger | 需要详细跟踪的非 Bug 需求分类、确认状态、进度链接与结果 | Bug 细节、已有小记录的重复正文 |
| Requirement Record | 背景、确认范围、方案、验收、依赖、影响与需求级验证 | 与需求无关的全局设计 |
| Decision Record | 数据/架构/API 等重大方案、备选项、理由、用户确认和回滚口径 | 日常实现流水账 |
| Bug Tracker | 现象、影响、根因、修复和验证 | 常规优化 |
| PDD | 产品定位、范围、体验、用户流程和验收 | 低层实现细节 |
| PRD | 技术约束、模块、接口、数据、兼容和验证 | 逐条需求流水账 |
| UI Guide | 视觉、交互、状态、组件和响应式规则 | 业务根因 |
| Project Progress | 项目当前口径、阶段和里程碑 | 每次细节改动 |
| Feature Progress Ledger | 大任务功能进度文档的位置、状态和最近更新时间 | 阶段明细和验证证据 |
| Feature Progress Record | 某个大任务的阶段计划、进度、DoD、证据、阻塞和下一步 | 无关任务的进度 |
| Business Flow | 指定业务域的入口、主链路、状态、异常和边界 | 无关模块说明 |

## 事实更新条件

一处主记录保存目标、范围、变化、验证和下一步；额外文档只随实际事实变化更新：产品目标/行为更新 PDD，架构/接口/数据更新 PRD，交互规范更新 UI Guide，业务状态流转更新 Business Flow，运营变化更新对应运行文档。路径变化才更新地图，实质取舍才记 DEC。沿用项目实际名称，可合并职责，不逐份写“无需更新”。仅构建或重新打包不新增需求，除非项目另有规定。

## 跨模块记录与验收

满足下列任一条件时，非 Bug 需求必须创建详细需求记录：同一持久化资源有多个写入入口或读取方；状态跨 API、SSE、确认卡、缓存或后台任务传播；改变跨模块契约、跨运行时行为或权限边界。单纯涉及图片、文件、Skill 或 MCP 名称不触发升级。

记录只覆盖实际受影响的模块，并至少写明：

- 写入入口；
- 读取方、刷新方式与重启后的恢复路径；
- 失败、取消、回滚、安全和平台边界；
- 已检查但不受影响的模块及理由；
- 行为验收矩阵（场景、前置条件、操作、预期结果、验证状态）。

单文件、无持久化状态、无跨端影响的改动可以只写简版台账。跨模块 Bug 仍只进入 Bug 台账；条目补充影响范围、关联流程检查和可复现或可验证的用户行为。

需求只有在影响分析、相关文档与行为验收均已回填后才能标记完成。真实环境、凭据或目标平台不可用时，记录“待实机回归”的具体用户路径和条件；静态检查、构建或接口测试不能替代该项验证。

## 记录之间的链接

- 需要详细跟踪的非 Bug 需求在需求台账中有唯一 ID；小记录沿用已有 ID 或日期，不重复登记。
- 重大决策关联 REQ 或 BUG 主记录；数据表或 DDL 变更还必须写明用户确认的方案与时间。
- 大任务的需求/Bug 主记录链接功能进度，进度索引链接对应 REQ 或 BUG；保留导航，不复制正文。
- Bug 如果由特定需求引入，必须链接该 REQ；功能进度文档若处理 Bug，也链接 Bug ID。
- 完成时，验证证据只保存一处，其余记录链接该来源；Git 项目按主包执行循环安排事实同步与最终 verify，避免记录结果时反复使指纹失效。
