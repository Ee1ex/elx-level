# 3.0 可选 oil 技能接入与场景验证

2026-11-21。源码基于 [ELX 2.2 基线](https://github.com/Ee1ex/elx-level/tree/c9a2c9e2108b175a20b8d958edba7185c2ab1536)，对照 [oil 上游原版](https://github.com/oil-oil/oil-dev-skills/tree/9bcd9000cfd08ef40546420f403e04a4df1c31f2)。主入口按需指向[调用规则](../references/oil-dev-skills.md)。安装器仍按现有清单独立安装 Level。源码包版本为 3.0，状态 Schema 为 2.0。

## 四级行为评测

评测使用隔离的合成项目。评测者从候选包的 `SKILL.md` 进入，仅收到用户请求、项目与可用技能条件，不读取预期答案。修改型任务检查实际文件、基线、测试输出及本地 Git 状态。安装可见性、没有独立审查者和用户拒绝安装是指定的宿主条件。

| 场景 | 观察到的结果 |
| --- | --- |
| LEVEL 1 离线按钮，宿主无 oil | 修改 `提交` 为 `保存`，同一检查核实点击动作仍为 `save_settings`。未加载 oil 指引、检查安装或弹出提示。 |
| LEVEL 2 在线按钮，宿主已有六项 | 同一按钮用例通过。沿用现有变更记录，无额外方案、原型、oil 调用或安装提示。 |
| LEVEL 1 离线存储格式 | 用旧样例读出 `old sample`，内存往返复现旧写入入口会丢失分组。用已装的 `oil-plan` 比较另存、旧客户端回写及兼容取舍。实际打包验收留到有构建产物后。 |
| LEVEL 2 公开注册的默认角色 | 在内存中验证新用户为普通成员、仅管理员可管理他人。即使改动只涉及一个默认值，仍先明确获权对象和恢复方法。用户拒绝安装后继续分析，实际 Diff 的独立审查留给审查者。 |
| LEVEL 3 维护者已接受的 Issue | 复现 `65` 秒显示为 `1:5`，局部修复后 `65/125/130` 秒分别得到 `1:05/2:05/2:10`。沿用 Issue 与仓库回归，不重做方案或引导安装。远程 CI 未运行。 |
| LEVEL 4 订单、支付、库存可行性 | 从已有接口识别支付回调可关联订单、库存超时无法查证预留结果。用已装的 `oil-plan` 比较先付款与先预留，指出进入实施前的决定。未创建资源，项目 Git 工作区保持干净。 |
| 缺少审查技能，用户跳过安装 | 夹具只有原版 `oil-plan`，实际 Diff 将 `name` 改为 `title`。评测者解释作者来源、当前项目目录及三项选择。用户跳过后用同一输入对比 HEAD 与工作区，复现旧数据触发 `KeyError`。保留待独立审查状态。 |
| 只查工作树 | 已装原版 `oil-govern` 的 `audit_repo.py --scope board --json` 在 Windows 离线返回 `cleanable=[]`。两棵工作树中一棵有未跟踪资料，清理候选为零。分支、文件与两棵工作树的状态回读一致。 |
| 原因不明的离线导入故障 | 用原版 `oil-bug-fix` 在内存中复现 LF 与 CRLF 导入差异。两组各重复十次，只有 CRLF 在标签末尾留下回车。局部调用链已明确，跳过全仓探索。夹具十个文件前后哈希一致。 |
| 只了解外部 CLI 复核选项 | 阅读 `oil-delegate` 的执行器权限规则，列出需决定的执行器、可发材料、读写范围及费用。解释直接指定执行器时要显式只读，未启动执行器或发送样例。 |

初轮两个按钮任务均在行为验收时通过。旧任务夹具预填的业务路径遗漏了 `verify` 改写的三份已跟踪证据，导致第一次本地提交资格检查被拒。核对差异、补齐三个准确路径并重新验证后，两个本地提交均成功。这一发现已补入[执行循环](../references/personal-execution-loop.md)，沿用原有提交范围检查。

在两份新夹具上由另一位评测者复验。LEVEL 1（无 oil）与 LEVEL 2（已装六项）均在第一次验证前登记相应证据路径，一次 `verify`、一次 `git-policy local_commit` 即通过。两个提交都只有 `ui.py`、现有变更记录和三份验证文件，提交后工作区干净。两项任务均为零次 oil 指引读取、安装探测、安装提示和委托。评测者额外查过一次任务登记命令的帮助，现已在[状态协议](../references/state-protocol.md)指明可复用的登记方法。此处统计的是这些样例的实际决策与命令次数。

## 安装和版本兼容

- 在独立 Windows 项目中从源码安装，仅在包内发现 Level 自己的一个 `SKILL.md`。按安装清单核对文件内容。旁边的六个原版技能共 33 个文件，安装前后逐文件 SHA-256 相同。安装回归还覆盖已有单个 oil 技能和完全未安装 oil 的项目。
- 在合成仓库运行原版 `repo_map.py` 与 `review_helper.py`，均返回 `OK`，后者识别到实际修改的 `store.py`。这两项是 Windows 只读脚本冒烟验证。
- 用 2.2 CLI 创建合成项目。3.0 的 `validate` 能读取原状态，同 Schema 的 `migrate` 保持原文件字节。执行原有 `status` 刷新时保存 2.2 备份，将工作流版本更新为 3.0，项目等级、阶段、权限及 Schema 2.0 均保留。
- `python -m unittest discover -s tests` 在原始 2.2 和候选 3.0 上均通过 144 项。候选源码与隔离安装的 `doctor` 和 `validate-package` 均通过，Skill Creator 格式检查通过。场景库共 45 项，ID 唯一、引用文件均存在；上表列出本轮实际执行的场景。
- 基线与候选的 Windows 单元测试使用独立进程，设置 `PYTHONUTF8=1`、`PYTHONDONTWRITEBYTECODE=1` 和 `GIT_CONFIG_COUNT=0`。最后一项仅用于这些本地测试，避免宿主注入的空 Git 配置值在子进程中丢失。未进行线上发布、真实外部模型委托或生产数据验证。
